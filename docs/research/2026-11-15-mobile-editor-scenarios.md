# Мобильный редактор: длинные группы, превью и Back

Продолжение исследования от 15 ноября 2026. Приложение не изменено. HEAD: `eb9f0bb1dc2e8dda305f7f0b93b7277f13b5fe3d`; Hub для этого шага: `ff148a1644f71a31cb599cab46a1e0752d2dbc64`. Предыдущий [UX-отчет](2026-11-15-mobile-editing-ux-review.md) сохранен как исходное исследование. Ниже уточняется предложенная там организация инструментов.

## Что изменилось в рекомендации

Опасение о маленьком превью подтвердилось. Одновременно показывать несколько ползунков удобно в короткой группе и при достаточной высоте, но нельзя делать это обязательным шаблоном для всех режимов и всех телефонов. На невысоком экране три ползунка заметно уменьшают изображение.

После сравнения основной кандидат — **один непосредственно доступный ползунок с быстрым переключением между параметрами выбранной группы**. Он открывается сразу при выборе инструмента, без промежуточного списка и без отдельного экрана на каждый числовой параметр. Параллельно показан вариант с несколькими ползунками, чтобы пользователь оценил разницу самостоятельно. Это предложения для выбора, а не утвержденный финальный дизайн.

Для длинного ASCII нужны небольшие смысловые группы: сетка, интервалы и подбор, символы, фон. Разделы и подгруппы переключаются внутри открытых инструментов, не создавая цепочку «Назад». Длинный редактор набора символов, импорт палитры и выбор файла могут занимать отдельный экран. Числовые свойства, чей эффект нужно оценивать глазами, следует по возможности оставить с видимым результатом независимо от того, считаем ли мы их основными или расширенными.

«Основные» и «расширенные» в этом исследовании — гипотеза организации. Аналитики частоты использования нет; объявлять интервалы или алфавит доказанно редкими нельзя.

## Наглядное сравнение

Подготовлены два интерактивных макета с реальным шрифтом, цветами и снимками результатов всех семи алгоритмов. Они показывают компоновку, переключения параметров и переход в отдельный редактор символов. Изображения получены из текущего renderer на встроенном примере. Сам renderer к макетам не подключен: тон демонстрируется CSS-фильтром, остальные значения показывают состояние интерфейса и предполагаемый путь регулировки. Макеты не предназначены для оценки качества алгоритмов, экспорта или импорта.

| --------------------------------------------------------------------------------- | ------------------: | ----------------------------: |
| Экран 393×852: видимое изображение                                                |          328×410 px |                    369×461 px |
| Экран 320×640: видимое изображение                                                |          148×185 px |                    213×266 px |
| Изменить три параметра и вернуться к обычному превью, без учета самих регулировок | 2 служебных нажатия |           4 служебных нажатия |
| Переключение к соседней регулировке                                               |      Сразу доступна |      Одно нажатие по названию |

Это измерения конкретного макета на конкретном изображении, не обещание будущих размеров. Картинка с другими пропорциями даст другой выигрыш. В нынешнем приложении тот же сценарий с возвратом к обычному превью требует 8 служебных нажатий, когда коррекция уже включена.

Макеты сохраняют область касания Slider высотой 44 px. Контрол не перемещается во время перетаскивания, панель не становится прозрачной, изображение не перекрывается активным ползунком. Высота длинной формы ограничена; прокручивается ее содержимое. Выделение подгрупп не означает, что все поля одновременно должны появиться под изображением.

Для проверки короткого экрана у макета есть настройка размера 393×852 / 320×640 / 430×932. Кнопка «Назад» над изображенным телефоном моделирует последовательность закрытия уровней. Она не управляет браузерной историей чата и не является проверкой физического жеста.

## Принцип Back

Предлагается небольшая история открытых экранов:

```text
Превью → Инструменты → Отдельный редактор символов / импорта
                   ← Back
       ← Back
```

Из отдельного редактора Back возвращает в исходный раздел инструментов. Из инструментов — на превью. Перемещения ползунка, выбор палитры, переключение «Стиль / Цвет / Тон» и раскрытие опций не становятся последовательными шагами Back. Из главного превью сохраняется нормальный выход браузера, без ловушки и без бесконечных записей истории. Выбор конкретных уровней — UX-решение hascii; это согласуется с обычной навигацией по предыдущим экранам, а не требование хранить каждый выбор. [Android navigation principles](https://developer.android.com/guide/navigation/principles).

Для установленного SvelteKit 2.70.3 есть штатный shallow routing через `$app/navigation` `pushState` / `replaceState`: новая запись на действительно открытый экран, замена состояния при смене раздела. Собственные обработчики edge swipe и история каждого значения не нужны. Контракт проверен по установленным типам и исходникам; актуальная внешняя документация SvelteKit уже описывает более новую версию API.

Важная оговорка к предыдущему исследованию: **переход назад по browser history и платформенный запрос закрыть временный UI — разные механизмы**. Нынешний Drawer уже построен на `<dialog>.showModal()` и синхронизирует закрытие. Браузер может закрыть его платформенным Back без новой записи истории. Предыдущая проверка `page.goBack()` воспроизводит уход по истории, а не физический свайп пользователя. Новая немодальная панель не получает такое поведение modal dialog автоматически. [HTML close requests](https://html.spec.whatwg.org/multipage/interaction.html#close-requests), [Chrome: platform controls dismiss dialog](https://developer.chrome.com/docs/modern-web-guidance/guides/ui-behaviors/platform-controls-dismiss-dialog).

Нельзя гарантировать, что сторонняя оболочка вообще отправит жест в web history: решение принадлежит приложению, в котором открыт WebView. До выпуска нужно проверить именно тот браузер/оболочку, где проявляется проблема. Новые `closedby` или `CloseWatcher` не предлагаются как универсальный обход этой границы. [Android WebView navigation](https://developer.android.com/develop/ui/views/layout/webapps/webview#navigate-web-page-history).

## Полный аудит сценариев

## Главный вывод

Все настройки ASCII действительно не помещаются в одну короткую панель из трёх ползунков: у «Фон + ASCII» доступны до **22 полей Settings**, у ASCII и ASCII FX — до **21**, вместе с общими Фото/Тон/режимом. Из них до **11 ползунков** в «Фон + ASCII» и ASCII FX. Большое превью можно сохранять при последовательном редактировании логических подгрупп; ограничивать всю функциональность тремя ползунками нельзя. Это вывод из состава интерфейса, а не проверка геометрии на устройстве. Источники: [Controls][C], [ArtControls][A], [Settings][T].

В `Settings` ровно **43 поля: 26 числовых, 5 boolean, 12 строковых/строковых union**. `ranges` содержит 25 числовых настроек; `resolution` — отдельный Select. `blur` присутствует в модели/defaults/ranges, но для него нет элемента UI и ни один активный renderer его не получает. Поэтому объединение нынешних видимых полей всех режимов — **42**, объединение нынешних Slider-параметров — **24**. Это не количество элементов на одном экране. Источники: [types][T], [defaults и диапазоны][S], [проекция входов renderer][M], [UI][C].

Нет предоставленных данных о частоте использования или продуктовой аналитики. Приоритеты ниже — **UX-гипотезы**, основанные на характере действия, зависимости от визуальной обратной связи и объёме ввода. Слова «основной» и «расширенный» не означают доказанную частоту использования. Нужно проверить прототипом с реальными задачами.

## Как считались элементы

Один count = одно поле `Settings`, которым можно управлять. Выбор режима — одно поле, хотя у ModePicker семь кнопок. Выбор палитры — одно поле, хотя карточек много. Presets, раскрытия details, ссылки, статусные сообщения, девять действий над алфавитом, загрузка, экспорт и расположение превью не добавлены к Settings-count.

«Основной Style/Color» ниже означает нынешние поля вне вложенных `<details>`, когда соответствующий раздел открыт. «Advanced» означает поля внутри нынешних details. Accordion разделов сам по себе не делает параметры Advanced. Общие `mode`, Фото, Тон и четыре пресета вынесены отдельно, чтобы не удваивать их в каждой колонке. В максимумах раскрыты все details и включены нужные ветки (`correction`, `paletteEnabled`, `pixelate`, `allowEmpty`, `matching='shape'`, `dither!='none'`). Это доступность при разворачивании всех разделов, а не утверждение, что приложение показывает все поля сразу. Источники: [композиция Controls][C], [условия ArtControls][A].

## Предлагаемое presentation: весь inventory из 43 полей

**Q — quick preview control:** прямой контрол в выбранном инструменте/подгруппе рядом с результатом. Это не требование держать все Q разных режимов на экране одновременно.

**E — extended panel:** расширенная подгруппа; после её выбора визуальные параметры продолжают редактироваться с результатом. «Расширенный» не означает принудительно закрыть превью, спрятать функциональность глубже или считать параметр редким.

**F — deliberate fullscreen text/file editor:** осознанный переход к длинному текстовому/файловому действию; превью может временно отсутствовать. После возврата сохраняются параметры и место в панели.

**H — hidden:** оставить поле совместимости в модели без контрола.

## Подгруппы для длинных режимов

Эти группы — предложение информационной архитектуры; окончательную высоту надо проверять на реальных viewport, с длинными русскими названиями, клавиатурой и безопасными областями. Общие Фото/Тон/Color не нужно физически встраивать целиком в Style.

### ASCII / Фон + ASCII / ASCII FX: четыре группы

| Группа                      | ASCII / overlay                                                                                                      | ASCII FX                                             | Поведение превью                                                                                                          |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Сетка и подбор**          | `fontSize`, `matching`, условный `shapeWeight` — до **3** полей                                                      | `cellSize`, `cellAspect` — **2**                     | Результат виден. Способ подбора не навязывается FX.                                                                       |
| **Шрифт и интервалы**       | `font`, `gapX`, `gapY` — **3**                                                                                       | То же — **3**                                        | Результат виден, интервалы можно сравнить друг с другом.                                                                  |
| **Алфавит и пустые ячейки** | Резюме/вход в `chars`; `allowEmpty`, условный `emptyThreshold` — **1–2 визуальных поля** + вход в текстовый редактор | То же                                                | Числовой threshold остаётся с превью; длинный алфавит и девять действий — осознанный F.                                   |

Так распределены все Style-поля трёх режимов. Color отдельно имеет «Палитра» (`paletteEnabled`, `palette`), «Дизеринг» (`dither`, `strength`) и вход «Импортировать палитру». Источники состава групп: [symbolStyle/characters][CS], [generic Color][CC], [различия математических inputs][M]. Группировка ограничивает число одновременных элементов осмысленной задачей, не удаляет остальные и не делает каждый ползунок отдельным полноэкранным маршрутом.

### Halftone: четыре группы с условными ветками

| Группа              | mono                                                     | CMYK                                     | duotone                                                                 |
| ------------------- | -------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------- |
| **Растр**           | `halftoneSize`, `halftoneShape`, `halftoneAngle` — **3** | То же — **3**                            | То же — **3**                                                           |

| **Смешение**        | Не показывать                                            | Не показывать                            | `halftoneBalance` — **1**                                               |

Все эти поля визуальные, включая native color picker: после выбора цвета результат должен быть снова виден. Не требуется прятать изображение на весь сеанс выбора Color или выставлять искусственный лимит в три поля: duotone-блок красок имеет четыре связанных поля. Если такое количество не помещается с нужным размером превью, допустимы отдельные подгруппы краски/бумаги или прокрутка панели; доказательство вместимости требует макета/измерения. `halftoneAngle` в CMYK **работает**: renderer использует основной угол и относительные +30°, +60°, +15° для остальных растров. Вторые ink/angle/offset/balance имеют смысл только в duotone и скрываются в остальных ветках с сохранением значений. Сдвиг перемещает весь второй слой, а не только фазу точек. Не удалять базовый угол CMYK при упрощении интерфейса. Источник: [renderHalftone][H].

## Ограничения изменения и критерии отсутствия регрессий

Предложение меняет расположение и размер открываемых групп. Семь алгоритмов и их входы остаются исходными: Pixel Art с автоматической палитрой; pixels с необязательной пикселизацией; Halftone с mono/CMYK/duotone; overlay с заливкой ASCII-ячеек; ordinary ASCII; двухцветный ASCII FX с собственным glyph profile; png2xp с фиксированными блоками и переключателем штриховки. Авторитетный перечень входов — [selectMode][M], а не единый универсальный набор ползунков.

Для будущей реализации необходимо проверить:

1. Любое поле из 42 видимых union-полей остаётся достижимым в прежних режимах и условиях. `blur` остаётся сохранённым и скрытым. Переключение mode/группы не сбрасывает значения других режимов. Preset остаётся отдельным действием со своим нынешним reset-контрактом. [M][M], [SP][SP], [mode projection tests][MT].
2. Сохраняются диапазоны, шаги, defaults, семантика нулей и ветвление correction/pixelate/paletteEnabled/dither/matching/allowEmpty/color mode. Generic palette и dither не появляются в Pixel Art/Halftone. [S][S], [C][C], [A][A].
3. Для ordinary ASCII и overlay при `overlayFill=0` сохраняется идентичность результата; интервалы остаются входами ASCII FX; png2xp не начинает зависеть от chars/font; `opacity` не меняет нынешний смысл заливки однотонных ASCII-участков. [engine][G], [glyph profile][GP], [mode tests][MT], [engine tests][GT].
4. Mono/CMYK/duotone, три формы, крайние углы/размеры, выбор бумаги/красок/баланса и смещения второго слоя остаются доступны; чистые белые поля и цветные пересечения не деградируют. [Halftone][H], [Halftone tests][HT].
5. Результат во время числовой визуальной правки остаётся видимым; переходы Q↔E и F↔панель сохраняют значения, текущую группу, прокрутку и возвращают фокус к вызвавшему действию. Нынешняя mobile-логика уже сохраняет место и фокус для одного числового параметра; это поведение нельзя потерять при группировке. [Editor][E], [ParameterRange][PR].
6. Клавиатура длинного алфавита и формы Lospec не обязана сосуществовать с большим изображением. После выхода доступны прежний результат/ошибка и путь исправления. Проверить невалидный/пустой алфавит, Unicode, 512 уникальных символов, отказ localStorage, pending/error/success импорта, смену файла во время обработки и готовность PNG. [EditorModel][EM], [glyph profile][GP], [engine tests][GT].

## Подробные источники о Back

## Восемь выводов: факты отдельно от решения

1. **Факт платформы:** Back обычно снимает текущий экран со стека и возвращает к предыдущему; из корневого экрана он может покинуть приложение. Android различает Back и Up: Up никогда не выходит из приложения. **UX-решение для hascii:** открытый настоящий подредактор должен возвращать к инструментам, инструменты — к главному превью. На главном превью не следует строить ловушку, бесконечно отменяющую выход. [Android: Principles of navigation](https://developer.android.com/guide/navigation/principles).

2. **Факт веб-платформы:** запрос «закрыть текущий временный UI» и переход назад по истории — разные механизмы. HTML Standard допускает трактовку мобильного Back как close request: сначала закрывается активный close watcher; если закрывать нечего, браузер может перейти к предыдущей записи истории. Это зависит от платформы/реализации, а не является универсальной доставкой JS-события Back. **UX-решение:** сначала закрывать верхний временный слой; отдельный глубокий экран должен иметь нормальное место в навигации. [WHATWG: Close requests](https://html.spec.whatwg.org/multipage/interaction.html#close-requests).

3. **Проверенный факт установленного kit:** `Drawer` 0.3.0 уже оборачивает `Dialog`; тот рисует нативный `<dialog>`, вызывает `showModal()`, а `onclose` синхронизирует `bind:open=false`. В текущем редакторе не отключен стандартный `closeOnEscape=true`. Поэтому на поддерживающей платформе modal-dismiss может уже работать без отдельного history entry. `page.goBack()` и WebKit-эмуляция проверяют history traversal, **не** физический системный close request. Нельзя выдавать их результат за воспроизведение жеста в реальном WebView. Источники: `node_modules/svelte-ascii-ui/dist/overlays/Dialog.svelte:31–33, 103–109`, `Drawer.svelte:7–10`; [Chrome: Platform Controls Dismiss Dialog](https://developer.chrome.com/docs/modern-web-guidance/guides/ui-behaviors/platform-controls-dismiss-dialog).

4. **Факт о `closedby`:** `closerequest` разрешает запрос закрытия; `any` дополнительно разрешает клик/тап снаружи; у `showModal()` отсутствующий атрибут ведет себя как `closerequest`. `closedby="any"` не создает запись истории и не гарантирует перехват закрытия native-хоста. **Вывод для kit:** публичные props наследуют `HTMLDialogAttributes`, Svelte 5.57.3 содержит `closedby`, а kit передает остальные атрибуты в `<dialog>`, поэтому атрибут технически доступен. Но для Back его не нужно «добавлять на всякий случай»: modal уже открыт правильно, а backdrop kit уже закрывает своим поддерживаемым `closeOnBackdrop`. [HTML Standard: dialog](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element); локальные `Dialog.svelte.d.ts`, `Dialog.svelte:7, 17, 103`, `node_modules/svelte/elements.d.ts:965–968`.

5. **Проверка совместимости на дату исследования:** свежий BCD указывает `closedby`: Chromium 134+, Firefox 141+, Safari 27.3; `CloseWatcher`: Chromium 126+, Firefox 149+, Safari 27.3. В том же наборе данных Safari 27.3 имеет статус **beta**, текущая Safari — 27.2. Поэтому ни новый атрибут, ни собственный `CloseWatcher` нельзя считать общей опорой для всех целевых мобильных браузеров. Наличие API отдельно не доказывает, что конкретный host передаст свой жест странице. **Рекомендация:** нативное modal-dismiss оставить платформенным улучшением, не предлагать новый API как обязательное исправление. Источники: [BCD dialog](https://raw.githubusercontent.com/mdn/browser-compat-data/main/html/elements/dialog.json), [BCD CloseWatcher](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/CloseWatcher.json), [BCD Safari releases](https://raw.githubusercontent.com/mdn/browser-compat-data/main/browsers/safari.json). Старые кешированные страницы web-features не использованы для итоговых версий.

6. **UX-решение, а не запрет веб-стандарта:** вкладки «Фото / Стиль / Цвет / Тон», раскрытие «Дополнительно» и изменения Slider — управление внутри одной задачи; им не нужна последовательность Back. Смена раздела заменяет текущий state (`replaceState`) при необходимости его восстановления; disclosure остается локальным; Slider не вызывает navigation API. Группы ASCII можно разделить на часто используемые параметры прямо в панели и самостоятельную задачу «Набор символов…», не превращая каждую регулировку в экран. Основа выбора — одинаковая задача редактирования и сокращение навигации; нормативного запрета добавлять tabs в историю нет.

7. **UX-решение: максимум две глубины после главного превью.** `Превью → Инструменты выбранной группы → настоящий подредактор` (например, алфавит или импорт). Из подредактора Back возвращает в исходную группу инструментов с ее прокруткой; из инструментов Back закрывает панель. Между обычными Slider не появляется промежуточный экран. Для app-owned немодальной панели и настоящих подэкранов достаточно стандартного SvelteKit shallow routing: одна запись на открытый навигационный уровень, замена state при смене секции, ноль записей на значения. Установленная 2.70.3 поддерживает `$app/navigation` `pushState('', state)` / `replaceState('', state)`; `goto(..., { shallow:true })` в ее типах отсутствует. Источники: `node_modules/@sveltejs/kit/types/index.d.ts:3285–3405`, `src/pages/playground/ui/Editor.svelte`.

8. **Факт границы хоста:** Android-приложение само решает, вызвать ли `WebView.goBack()` при `canGoBack()` либо передать Back системному поведению. Шаги истории помогают, когда хост выполняет web-навигацию; они не дают странице власть над закрытием чужого WebView/Activity. **Рекомендация реализации:** не писать собственный listener свайпа, не добавлять бесконечные sentinel entries, не объединять без координации native modal-dismiss и независимый history handler. Проверить оба пути: browser history Back и физический жест на нужной оболочке. [Android: Navigate web page history](https://developer.android.com/develop/ui/views/layout/webapps/webview#navigate-web-page-history).

## Простая формулировка пользователю

Нормальное поведение здесь: Back закрывает открытый уровень интерфейса. Из редактора набора символов он возвращает к настройкам, из настроек — к превью. Выбор раздела, раскрытие дополнительных опций и движения ползунков не должны становиться отдельными шагами Back. Для этого нужна небольшая история экранов, а не история каждого выбора. Нативный dialog уже умеет закрываться платформенным способом там, где браузер и оболочка это поддерживают; конкретный жест WebView проверяется отдельно.
